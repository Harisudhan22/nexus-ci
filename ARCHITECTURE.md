# NEXUS-CI System Architecture

This document describes the architectural design and pipeline mechanics of the NEXUS-CI Evidence-Centric AI Criminal Intelligence Platform.

## 1. System Overview

NEXUS-CI is designed as a modular monolith integrating:
- **FastAPI Core Backend** serving REST APIs.
- **PostgreSQL Database** managing metadata, evidence records, raw/canonical entity indexes, findings, and audit logs.
- **Neo4j Graph Database** modeling the structural knowledge graph.
- **Next.js React Frontend** providing visual drawers, case registries, timeline chronological flow, and graph canvas representations.

```
       +---------------------------------------+
       |           Next.js Frontend            |
       +-------------------+-------------------+
                           |
                           | REST API
                           v
       +-------------------+-------------------+
       |            FastAPI Core               |
       +-------+-----------------------+-------+
               |                       |

     +---------+----------+  +---------+----------+
     |     PostgreSQL     |  |       Neo4j        |
     +--------------------+  +--------------------+

     | Text, Audit Logs   |  | Relations, Paths   |
     +---------+----------+  +--------------------+

     |  AI / NLP Pipeline |
     +--------------------+

     | RapidFuzz Scoring  |
```

## 2. Ingestion Processing Pipeline

When an investigator uploads an evidence file, it transitions through these stages sequentially:

```
[UPLOADED] ---> [HASHING] ---> [PARSING] ---> [NER EXTRACTION] ---> [RESOLUTION] ---> [NEO4J MERGE] ---> [ANALYTICS] ---> [FINDINGS] ---> [COMPLETED]
```

### Pipeline Stages:
1. **Validating**: Verifies file size limit (15MB), extension, and uploader clearances.
2. **Hashing**: Generates a SHA-256 fingerprint for forensic auditing.
3. **Parsing**: Runs deterministic parsers:
   - **PDF**: PyMuPDF parses textual layers.
   - **DOCX**: python-docx parses document lines.
   - **CSV**: pandas converts cells into JSON rows.
4. **Extracting**: Performs entity mentions scan:
   - **Phones**: Regex search matching Jio/Airtel/standard formats.
   - **Vehicles**: Regex matching Indian registration plates (e.g. TN01AB1234).
   - **Accounts**: Regex matching finance tags.
   - **Persons/Locations/Orgs**: spaCy Named Entity Recognition (`en_core_web_sm`).
5. **Resolving**: Checks for near-duplicate entities (e.g. "Ravi Kumar" vs. "R. Kumar") using **RapidFuzz** scoring:
   - Name Similarity: 40%
   - Phone Match: 25%
   - Vehicle Match: 15%
   - Case Overlap: 10%
   - Neighbor Co-occurrence: 10%
   If score > 60%, a pending `ResolutionCandidate` is logged for investigator review.
6. **Building Graph**: Adds validated entities to Neo4j. Relationships like `CALLS` or `TRANSFERS` are created with full provenance tags (`confidence`, `evidence_ids`, `occurrences`).
7. **Analyzing & Patterns**: NetworkX parses modularity clusters, degree centralities, and identifies cluster articulation points (Bridges). The findings engine runs patterns to flag anomalies.

## 3. Grounded Copilot (RAG) Mechanics

The Grounded Investigator Copilot uses a restricted context query process to ensure absolute grounding and eliminate AI hallucinations.

### Step-by-Step Flow:
1. **Keyword Scan**: Scans user questions against canonical entities list in the current case.
2. **Context Retrieval**:
   - Fetches target entity properties and co-occurring neighbors from Neo4j.
   - Fetches document text snippets referencing target aliases from PostgreSQL.
3. **Structured Prompt Compilation**: Feeds context and strict rules into LLM (OpenAI or Groq).
4. **Citations Grounding Check**: Cross-references citations (e.g. `[CDR-101]`) generated by LLM against actually retrieved document list. If a citation is invalid (unretrieved document), the citation is removed or "Insufficient evidence" is returned.
